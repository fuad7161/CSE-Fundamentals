# OS Basics — Process, Memory, Scheduling

Comprehensive definitions and explanations covering OS fundamentals, process management, memory management, and CPU scheduling.

---

## 1. Introduction to Operating System

### Definition of Operating System
An **Operating System (OS)** is a system software that acts as an intermediary between computer hardware and the user. It manages hardware resources (CPU, memory, storage, I/O devices) and provides services for running application programs.

### Objectives of OS
- **Convenience** — Makes the computer system easy to use
- **Efficiency** — Ensures optimal utilization of hardware resources
- **Extensibility** — Allows development, testing, and introduction of new system functions without interference
- **Resource Management** — Allocates CPU time, memory, and I/O devices efficiently

### Functions of OS
1. **Process Management** — Creating, scheduling, and terminating processes
2. **Memory Management** — Allocating and deallocating memory to processes
3. **File Management** — Organizing data into files and directories
4. **Device Management** — Managing I/O devices via device drivers
5. **Security & Protection** — Authentication, authorization, file permissions
6. **User Interface** — CLI or GUI for user interaction

### Components of OS
| Component | Function |
|---|---|
| **Kernel** | Core component — manages CPU, memory, devices; runs in privileged mode |
| **Shell** | User interface that accepts and interprets commands |
| **File System** | Organizes and stores data on storage devices |
| **Device Drivers** | Translate OS commands to hardware-specific instructions |
| **System Utilities** | Disk cleanup, antivirus, backup tools |

### Kernel ⭐
The **Kernel** is the central component of an OS that has complete control over everything in the system. It is the first program loaded on startup and remains in main memory. It handles:
- Process scheduling
- Memory management
- Interrupt handling
- I/O operations
- System calls

Types of kernels: Monolithic, Microkernel, Hybrid, Modular, and Layered.

### Shell ⭐
The **Shell** is a command-line interpreter that provides a user interface to access OS services. It accepts human-readable commands and translates them into instructions for the OS.
- **Bash (Bourne Again Shell)** — Default on most Linux distributions
- **PowerShell** — Windows shell with scripting capabilities
- **Zsh** — Extended Bourne shell with advanced features

### User Mode vs Kernel Mode
| Mode | Privilege | Access | Purpose |
|---|---|---|---|
| **Kernel Mode** | High (Ring 0) | Full hardware access | OS kernel runs here |
| **User Mode** | Low (Ring 3) | Restricted access | Application programs run here |

- Switching from user mode to kernel mode requires a **system call**.
- This separation provides **protection and stability** — a crash in user mode doesn't crash the entire system.

### Booting Process
The sequence of events from power-on to OS readiness:
1. **Power-On Self-Test (POST)** — Hardware checks
2. **BIOS/UEFI** — Locates boot device and loads bootloader
3. **Bootloader** (GRUB/LILO) — Loads the OS kernel into memory
4. **Kernel Initialization** — Sets up memory, processes, device drivers
5. **Init Process** — Starts system services and reaches runlevel/target
6. **Login Screen** — System ready for user

### BIOS vs UEFI
| Feature | BIOS (Legacy) | UEFI (Modern) |
|---|---|---|
| Interface | Text-based, keyboard-only | GUI support, mouse navigation |
| Boot Speed | Slower | Faster |
| Partition Table | MBR (up to 2TB) | GPT (up to 9.4 ZB) |
| Architecture | 16-bit | 32-bit or 64-bit |
| Security | No secure boot | Secure Boot support |
| Driver Support | Limited | Extensible driver interface |

### Types of OS ⭐

| Type | Description | Examples |
|---|---|---|
| **Batch OS** | Jobs grouped together and executed without user interaction | IBM OS/360 |
| **Multiprogramming** | Multiple programs in memory; CPU switches between them to keep busy | Early Unix |
| **Multitasking** | Multiple tasks share CPU via time-slicing (time-sharing) | Windows, Linux, macOS |
| **Multiprocessing** | Multiple CPUs/cores work simultaneously | Windows Server, Linux |
| **Multiuser** | Multiple users access same system simultaneously via terminals | Unix, Linux, Windows Server |
| **Distributed OS** | Multiple independent computers appear as a single system | Plan 9, Google Fuchsia |
| **Network OS** | Manages network resources; runs on servers | Windows Server, Novell NetWare |
| **Real-time OS (RTOS)** | Guarantees response within strict deadlines | FreeRTOS, VxWorks, QNX |
| **Embedded OS** | Runs on devices with limited resources (IoT, appliances) | Embedded Linux, Android Things |
| **Mobile OS** | Designed for smartphones and tablets | Android, iOS |

## 2. Evolution of Operating Systems

### First Generation (1940s–1950s)
- No OS — programmers interacted directly with hardware
- Used vacuum tubes, machine language
- Batch processing with punch cards

### Second Generation (1950s–1960s)
- Introduction of **batch processing systems**
- Monitor programs to automate job sequencing
- Transistors replaced vacuum tubes

### Third Generation (1960s–1970s)
- **Multiprogramming** OS developed (IBM System/360)
- Integrated Circuits (ICs) made systems more reliable
- Spooling and time-sharing introduced

### Fourth Generation (1970s–present)
- **Personal computers** with GUI
- Networking capabilities integrated
- Windows, macOS, Linux, Unix variants

### Notable Operating Systems History

| OS | Year | Key Features |
|---|---|---|
| **DOS** | 1981 | Single-user, single-tasking, CLI (Microsoft) |
| **UNIX** | 1969 | Multiuser, multitasking, portable, CLI (AT&T Bell Labs) |
| **Linux** | 1991 | Open-source Unix-like kernel (Linus Torvalds) |
| **Windows** | 1985 | GUI-based, multitasking (Microsoft) |
| **Android** | 2008 | Linux-based, mobile OS (Google) |
| **macOS** | 2001 | Unix-based, GUI (Apple) |

## 5. Process Management ⭐

### Program vs Process
| Aspect | Program | Process |
|---|---|---|
| Definition | Passive set of instructions | Active instance of a program in execution |
| Storage | Stored on disk (static) | Loaded in memory (dynamic) |
| Lifetime | Permanent | Temporary — from creation to termination |
| Resources | No resources allocated | CPU, memory, I/O allocated |

### Process States
```
New → Ready → Running → Terminated
         ↓          ↓
      Waiting    Blocked
         ↓
      Suspended
```
- **New:** Process is being created
- **Ready:** Process is ready to run, waiting for CPU
- **Running:** CPU is executing the process
- **Waiting/Blocked:** Process waiting for I/O or event
- **Terminated:** Process has finished execution

### PCB (Process Control Block)
The **Process Control Block** is a data structure in the OS kernel that stores all information about a process:
- **Process ID (PID)** — Unique identifier
- **Process State** — Current state (ready, running, etc.)
- **Program Counter** — Address of the next instruction
- **CPU Registers** — Saved context for resumption
- **CPU Scheduling Information** — Priority, queue pointers
- **Memory Management Info** — Page tables, segment tables
- **I/O Status** — List of open files, allocated devices

### Context Switching
**Context Switching** is the mechanism by which the CPU switches from executing one process to another. The OS saves the state (PCB) of the current process and loads the saved state of the next process. It involves overhead — time spent saving/loading registers, updating page tables, etc.

### Process Scheduling
The OS scheduler selects which process from the ready queue will be allocated the CPU. Goals include fairness, efficiency, and minimal response time.

### Process Queue
- **Job Queue** — All processes in the system
- **Ready Queue** — Processes in main memory, ready to execute
- **Device Queue** — Processes waiting for I/O devices

### Parent and Child Process
A process can create another process (child). In Unix/Linux, the `fork()` system call creates a child process, and `exec()` replaces the current process with a new program.

## 7. CPU Scheduling ⭐

### Scheduling Types
| Scheduler | Frequency | Function |
|---|---|---|
| **Long-term** | Low | Selects processes to load into memory (job scheduler) |
| **Medium-term** | Medium | Swaps processes in/out of memory |
| **Short-term** | High | Selects next process for CPU dispatch (CPU scheduler) |

### Scheduling Criteria
| Criterion | Description |
|---|---|
| **CPU Utilization** | Percentage of time CPU is busy (aim: 40–90%) |
| **Throughput** | Number of processes completed per unit time |
| **Turnaround Time** | Time from process arrival to completion |
| **Waiting Time** | Total time process spends in ready queue |
| **Response Time** | Time from request submission to first response |

### Scheduling Algorithms

| Algorithm | Description | Characteristics |
|---|---|---|
| **FCFS** (First Come First Served) | Processes executed in arrival order | Non-preemptive; simple; may cause convoy effect |
| **SJF** (Shortest Job First) | Process with smallest burst time first | Non-preemptive; minimal avg waiting time; starvation possible |
| **SRTF** (Shortest Remaining Time First) | Preemptive version of SJF | Preemptive; better response; overhead of remaining time tracking |
| **Priority Scheduling** | Highest priority process runs first | Can be preemptive/non-preemptive; starvation possible (aging solution) |
| **Round Robin** | Each process gets fixed time quantum | Preemptive; good response time; widely used; quantum sizing critical |
| **Multilevel Queue** | Processes categorized into queues | Each queue has its own scheduling algorithm |
| **Multilevel Feedback Queue** | Processes can move between queues | Most complex; used in modern OSes |

### Numericals:
- **Waiting Time:** Time spent in ready queue = Turnaround Time - Burst Time
- **Turnaround Time:** Completion Time - Arrival Time
- **Gantt Chart:** Visual timeline showing which process runs when

## 10. Memory Management ⭐

### Memory Hierarchy
```
Registers > Cache (L1/L2/L3) > RAM > SSD > HDD
(Fast, small, expensive) → (Slow, large, cheap)
```

### Logical Address vs Physical Address
| Aspect | Logical Address | Physical Address |
|---|---|---|
| Definition | Address generated by CPU (virtual) | Actual address in RAM |
| Visibility | Visible to program | Not visible to program |
| Space | Logical Address Space | Physical Address Space |
| Generation | By CPU during execution | Mapped from logical by MMU |

### Address Binding
Mapping logical addresses to physical addresses can happen at:
- **Compile time** — Absolute code (fixed address)
- **Load time** — Relocatable code (address determined at load)
- **Execution time** — Dynamic binding (address resolved at runtime)

### Swapping
Moving a process between main memory and secondary storage (swap space) to free up RAM. Include-out: entire process moves out, another moves in.

### Contiguous Allocation
Each process occupies a single contiguous block of memory.
- **Fixed Partitioning** — Memory divided into fixed-size partitions (leads to internal fragmentation)
- **Dynamic Partitioning** — Partitions created dynamically based on process needs (leads to external fragmentation)

### Fragmentation
| Type | Description |
|---|---|
| **Internal Fragmentation** | Allocated memory block is larger than needed; space wasted inside the block |
| **External Fragmentation** | Total free memory is sufficient but not contiguous; scattered small holes |

### Compaction
Reorganizing memory to combine all free memory into one large contiguous block (solves external fragmentation but is costly).

## 11. Paging ⭐

### Pages and Frames
- **Pages:** Fixed-size blocks of logical memory (typically 4 KB)
- **Frames:** Fixed-size blocks of physical memory (same size as pages)

### Address Translation
```
Logical Address → Page No. + Offset
                     ↓
              Page Table → Frame No.
                     ↓
Physical Address = Frame No. + Offset
```

### Page Table
A data structure that maps **page numbers to frame numbers**. Each process has its own page table.

### TLB (Translation Lookaside Buffer)
A small, fast cache in the CPU that stores recent page-to-frame mappings. Speeds up address translation (reduces need to access page table in memory).

### Page Fault
When a referenced page is **not in main memory**, a page fault occurs. The OS must:
1. Check if the reference is valid
2. Find a free frame
3. Load the required page from disk into the frame
4. Update the page table
5. Resume the process

### Numericals:
- **Physical Address Calculation:** Frame Number × Frame Size + Offset
- **Number of Frames:** Physical Address Space / Frame Size
- **Offset Bits:** log₂(Page Size)

## 12. Segmentation

### Segment Table
Memory is divided into **variable-sized segments** (code, data, stack, heap). The segment table maps:
- **Segment Number → Base Address + Limit**

### Address Translation
```
Logical Address → Segment No. + Offset
                     ↓
              Segment Table → Base + Limit Check
                     ↓
        Physical Address = Base + Offset (if Offset < Limit)
```

### Paging vs Segmentation

| Aspect | Paging | Segmentation |
|---|---|---|
| Division | Fixed-size pages | Variable-size segments |
| User Visibility | Invisible to user | Visible (programmer manages) |
| Fragmentation | Internal | External |
| Table | Page Table | Segment Table |
| Protection | Page-level | Segment-level |

## 13. Virtual Memory ⭐

### Virtual Memory
A technique that allows a process to execute even if it is **larger than physical memory**. It separates logical memory as seen by the user from physical memory. The OS keeps only active pages in RAM and the rest on disk.

### Demand Paging
Pages are loaded into memory **only when they are referenced** (on demand). Reduces I/O, memory usage, and speeds up multiprogramming.

### Thrashing
A condition where the system spends more time **swapping pages in and out** than executing the actual process. Caused by too many processes competing for too few frames. Leads to severe performance degradation.

### Working Set
The set of pages that a process is currently using. The OS must ensure each active process has enough frames for its working set to prevent thrashing.

### Page Replacement Algorithms ⭐

| Algorithm | Description | Key Feature |
|---|---|---|
| **FIFO** | First-In, First-Out page replacement | Oldest page in memory is replaced; may cause **Belady's Anomaly** |
| **LRU** (Least Recently Used) | Replaces page not used for the longest time | Good performance; costly to implement |
| **Optimal** | Replaces page that will be used furthest in future | Theoretical best; impossible to implement (needs future knowledge) |
| **LFU** (Least Frequently Used) | Replaces page with smallest usage count | Count-based; counters must be maintained |
| **Second Chance (Clock)** | Circular FIFO with a reference bit | Gives pages a second chance before replacement |

### Numerical Page Fault Problems
Steps to solve:
1. Track page references in sequence
2. Maintain frame contents at each reference
3. Apply the replacement algorithm when a page fault occurs
4. Count the number of page faults
